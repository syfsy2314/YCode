# YCode 交互式对话 Spec

> 状态：已批准

## 背景

YCode 是一个从零构建的 Windows 命令行 AI 助手，长期目标是发展为类似 Claude Code 的 Coding Agent。首个开发阶段聚焦纯对话能力：用户从终端启动 YCode 后进入交互式界面，可以连续输入问题，并实时看到大模型生成的回复。

## 目标

- 提供可持续交互的终端对话界面。
- 回复生成过程中持续输出内容，不等待完整回复生成。
- 在当前运行会话中保留多轮对话上下文。
- 支持 Anthropic Claude 和 OpenAI 两种 API 后端。
- 通过一个 YAML 配置文件管理多个供应商配置，并选择当前配置。
- Claude 启用 extended thinking 时，单独流式展示 Thinking 内容。
- 在每轮请求期间显示实时响应耗时，并在本轮结束后保留总耗时。
- 使用 Markdown 渲染模型的最终回答，使常用文本格式在终端中清晰可读。
- 统一不同供应商的行为，为以后增加新的 API 后端预留清晰扩展点。
- 首期只实现对话闭环，为后续 Coding Agent 能力打基础。

## 功能需求

- **F1：启动与配置加载**  
  用户启动 YCode 后，程序从当前工作目录开始逐级向上查找最近的 `.ycode/config.yaml`；用户显式指定配置路径时使用该路径且不执行目录搜索。程序读取 YAML 配置，找到 `active` 指定的供应商配置，只对该活动配置完成完整校验后进入交互式对话界面。

- **F2：多供应商配置**  
  YAML 顶层包含 `active` 和 `providers`。`providers` 中每项必须包含唯一的 `name`，用于匹配 `active`。`active` 指向的配置还必须包含以下字段：
  - `protocol`：`anthropic` 或 `openai`。
  - `model`：模型名称。
  - `base_url`：API 请求地址。
  - `api_key`：明文密钥或 `${ENV_VAR}` 引用。
  - `thinking`：可选布尔值，控制 Claude extended thinking。
  
  未激活配置除 `name` 外可以暂时缺少其他字段，也可以保留尚未可用的字段值；这些字段在该配置被选为 `active` 前不参与完整校验。

- **F3：配置校验**  
  启动时检查配置文件查找结果、顶层结构、`active`、所有配置的 `name` 及名称重复情况，并只对 `active` 指向的配置检查必填字段、协议值、字段组合及环境变量。未激活配置的非 `name` 字段不校验、不解析环境变量，也不因字段缺失或无效阻止启动。找不到 `.ycode/config.yaml`、显式路径不存在或活动配置校验失败时显示具体原因并退出，不进入对话界面。

- **F4：供应商路由**  
  `protocol: anthropic` 使用 Claude Messages API；`protocol: openai` 使用 OpenAI Chat Completions API。切换 `active` 后无需修改代码。

- **F5：交互式对话**  
  用户进入 TUI 后可以反复输入问题。每次提交非空输入后，YCode 调用当前供应商并显示回复。

- **F6：流式回复**  
  两种供应商都通过 SSE 接收响应。收到文本增量后立即追加到终端，不等待完整回复生成后再统一显示。

- **F7：当前会话多轮记忆**  
  当前进程内保存用户消息和 AI 回复，并在后续请求中携带历史。正常退出后历史清空，不写入磁盘。

- **F8：Claude extended thinking**  
  当 Claude 配置的 `thinking: true` 时，请求扩展思考，并在独立的 Thinking 区域流式展示思考内容，然后展示最终回复。模型不支持或 API 拒绝时显示明确错误，不静默降级。OpenAI 配置不得启用该字段。

- **F9：统一 Provider 行为**  
  TUI 和会话管理不直接依赖具体供应商。不同后端向上提供统一的文本增量、思考增量、完成和错误行为。

- **F10：错误恢复**  
  API 认证失败、网络失败、限流、服务端错误或流中断时，显示可理解且不包含密钥的错误信息。单次请求失败后保留已有对话，用户可以继续输入重试。

- **F11：安全退出**  
  提供明确的退出方式；退出时正常关闭网络连接和终端界面，不打印异常堆栈。

- **F12：响应耗时**  
  用户提交非空消息后立即开始并显示本轮响应计时，在首个流式增量到达前计时也必须可见并持续更新。流结束或本轮失败后停止计时并显示本轮总耗时；用户提交下一轮消息时重新从零开始计时。

- **F13：Markdown 回答渲染**  
  接收流式文本增量时，回答区域按原始文本直接追加显示，不在增量阶段解析 Markdown。收到本轮完成事件后，使用累计的完整回答进行一次整体 Markdown 渲染，并以渲染结果替换流式原文。最终渲染至少支持标题、粗体、斜体、行内代码、围栏代码块、列表、引用和链接的终端友好展示。Thinking 区域始终以纯文本显示，不进行 Markdown 渲染。

- **F14：输入提示区**  
  等待用户输入时，输入区按“上横线、输入行、下横线、提示区”的顺序显示。`❯ Send a message...` 位于两条等宽的普通横线之间；下横线之外另起一行显示静态提示 `? for help`。提示区与输入边界分离，不使用反色工具栏、背景色块或完整矩形边框。本期 `? for help` 只作为未来帮助、快捷入口或 Skill 提示的展示位置，不响应 `?` 命令。上下横线共用一个内部颜色样式入口，默认使用低对比度灰色；该入口允许以后替换颜色，但本期不增加 YAML 字段或 TUI 设置。

- **F15：用户消息展示**  
  用户提交非空消息后，终端滚动区使用无边框、低对比度背景板突出该消息。背景板宽度与输入区一致且最长为 100 列；首行前显示蓝色 `❯`，不支持 Unicode 时回退为 `>`。多行内容在同一背景板内显示并与正文列对齐，不显示 `You` 标签。

## 非功能需求

- **N1：平台范围**  
  首期仅保证 Windows 10/11 环境运行，支持从 PowerShell 和 Windows Terminal 启动。

- **N2：流式响应体验**  
  收到 SSE 文本或 Thinking 增量后应立即交给界面渲染，不人为缓冲到完整句子或完整回复。界面更新不得阻塞后续网络事件接收。

- **N3：供应商可扩展性**  
  新增供应商时，主要工作应局限在新的 Provider 实现和注册配置中，不要求修改会话管理和 TUI 主流程。

- **N4：协议隔离**  
  Anthropic 与 OpenAI 的请求格式、认证方式和 SSE 事件解析封装在各自 Provider 内，不向上层泄漏供应商专用数据结构。

- **N5：安全性**  
  API Key 不得出现在正常输出、错误信息或日志中。`${ENV_VAR}` 只在内存中解析，不回写带有真实密钥的配置文件。

- **N6：可恢复性**  
  单次请求失败或流中断不得导致整个程序崩溃；除非配置本身无效，否则用户应能返回输入状态并继续对话。

- **N7：可测试性**  
  配置加载、Provider 事件转换、多轮历史和错误处理必须能通过模拟响应测试，不依赖真实 API Key。TUI 对话流程需要至少一个可自动或半自动执行的端到端测试。

- **N8：依赖控制**  
  首期只引入完成配置、官方 API 调用、异步交互和终端界面所需的依赖，不加入 tool use、Agent 框架或持久化相关依赖。

- **N9：敏感错误处理**  
  正常用户错误只显示简洁说明；调试细节与用户提示分离，不直接向终端输出包含请求头、完整响应或密钥的异常对象。

- **N10：配置兼容边界**  
  自定义 `base_url` 必须实现对应的 Anthropic Messages 或 OpenAI Chat Completions 协议；YCode 不负责兼容私有或非标准事件格式。

- **N11：计时准确性**  
  响应耗时使用不受系统时间校准影响的单调计时来源，界面计时刷新不得阻塞 SSE 接收或文本渲染。

- **N12：Markdown 流式稳定性**  
  增量阶段的纯文本追加不得因未闭合或跨增量拆分的 Markdown 标记而中断、丢失或重排内容；仅在收到完成事件并取得完整回答后执行一次 Markdown 解析和整体渲染。

- **N13：输入布局稳定性**  
  上下横线、输入行和提示区在输入等待期间必须同时可见；提交、取消或退出后不得残留动态提示区域或破坏后续终端输出。终端最后一列应预留给自动换行控制，避免边界折成两行。横线颜色通过输入组件的内部样式参数或等价的集中式样式令牌提供，上下边界必须使用同一语义颜色，避免在组件中分散硬编码。

## 不做的事

- Tool use、函数调用及任何 Agent 工具系统。
- 读取、搜索、创建、修改或删除本地文件。
- 执行 Shell、PowerShell 或其他系统命令。
- 代码生成后的自动应用、补丁、代码编辑或项目操作。
- 对话历史持久化、恢复上一次会话或管理多个会话。
- 在 TUI 内编辑配置、切换供应商或选择模型；配置在启动时读取，切换后需要重新启动。
- 多供应商自动故障转移或自动选择模型。
- Linux、macOS 或 Web/GUI 客户端支持。
- API Key 加密存储、系统凭据管理或账号登录流程。
- Token 用量、费用统计、上下文自动压缩或历史裁剪。
- OpenAI 推理过程展示；Thinking 区域仅用于 Claude extended thinking。
- 代码语法高亮、自定义主题系统等进一步的界面美化；首期仅实现常用 Markdown 结构的终端渲染。
- 非标准 Anthropic/OpenAI 协议的专门兼容适配。
- 插件系统、MCP、子代理或多代理协作。
- `? for help` 对应的帮助命令、快捷入口交互、Skill 发现或 Skill 执行；首期只预留静态提示区。
- 面向用户的横线颜色配置或完整主题系统；首期只保留代码内部样式入口。

## 验收标准

- **AC1（F1、F5）**  
  在项目目录放置有效的 `.ycode/config.yaml`，从该目录或任意子目录启动 YCode 后，程序加载距离当前目录最近的配置，终端进入交互界面并显示输入提示；用户可以输入一条消息并提交。显式指定配置路径时，程序只使用指定文件。

- **AC2（F2、F4）**  
  YAML 中存在多个 Provider 配置时，YCode 只使用 `active` 指向的配置。修改 `active` 并重新启动后，请求切换到对应供应商、模型和 `base_url`。

- **AC3（F2、F3）**  
  逐级向上找不到 `.ycode/config.yaml`、显式配置路径不存在、YAML 无法解析、活动配置不存在、配置名称缺失或重复、活动配置必填字段缺失或活动配置协议无效时，YCode 显示包含查找范围或字段定位的错误并以非零状态退出。

- **AC4（F2、F3）**  
  活动配置的 `api_key` 可以直接填写，也可以使用 `${ENV_VAR}`。环境变量存在时能够正常认证；不存在时启动失败并指出变量名。未激活配置引用的环境变量不存在时不影响启动。

- **AC5（F4）**  
  Anthropic 配置向对应 `base_url` 的 Messages API 发起请求；OpenAI 配置向对应 `base_url` 的 Chat Completions API 发起请求。测试能够观察到正确的认证方式、模型和消息内容。

- **AC6（F6）**  
  模拟服务先发送一个 SSE 文本增量、延迟后再发送后续增量和结束事件时，第一个增量必须在结束事件到达前显示在终端中。

- **AC7（F7）**  
  用户完成第一轮对话后发送第二个问题，第二次 API 请求包含第一轮用户消息、第一轮完整 AI 回复和第二个问题。

- **AC8（F7）**  
  正常退出 YCode 后不产生会话历史文件；重新启动时第一条请求不包含上一次运行的消息。

- **AC9（F8）**  
  Claude 配置设置 `thinking: true` 时，请求启用 extended thinking；收到 Thinking 增量后，它们显示在独立区域，最终文本显示在回答区域。

- **AC10（F8）**  
  Claude 配置未设置 `thinking` 或设置为 `false` 时，不请求 extended thinking，也不显示 Thinking 区域。

- **AC11（F8）**  
  活动 OpenAI 配置设置 `thinking: true` 时，配置校验失败并明确说明该字段只适用于 Anthropic，不发送 API 请求。未激活 OpenAI 配置中的该字段不参与校验。

- **AC12（F9）**  
  Anthropic 和 OpenAI 的流式响应均被转换成相同类别的上层事件。会话和 TUI 测试不需要判断供应商专用 SSE 事件名称。

- **AC13（F10）**  
  模拟认证失败、限流、网络断开、服务端错误和流中错误后，界面显示经过整理的错误信息并返回输入状态，用户可以继续提交下一条消息。

- **AC14（F10、N5、N9）**  
  配置校验错误、API 错误和异常输出中均搜索不到配置中的真实 API Key。

- **AC15（F11）**  
  用户执行退出操作后，YCode 正常结束，网络客户端被关闭，终端恢复可用且不显示异常堆栈。

- **AC16（N3、N4）**  
  使用测试用的虚拟 Provider 接入统一接口时，无需修改会话管理和 TUI 主流程即可完成一轮流式对话。

- **AC17（N7）**  
  不使用真实 API Key，通过本机模拟 Anthropic 和 OpenAI SSE 服务完成配置加载、流式输出、多轮上下文、Thinking 展示和错误恢复测试。

- **AC18（N1、N7）**  
  在 Windows 环境连接本机模拟服务执行端到端测试：启动 YCode、输入两轮消息、观察流式输出、退出程序，完整流程通过。

- **AC19（N5、N7）**  
  项目提供不含真实密钥的示例配置，以及 Anthropic 和 OpenAI 的手动冒烟测试步骤。真实 API 测试由用户填写 Key 后执行，不作为自动化验收前置条件。

- **AC20（F12、N11）**  
  用户提交消息后，在模拟服务发送首个增量之前即可观察到从零开始增长的响应耗时；流正常结束或异常结束后计时停止并保留本轮总耗时。再次提交消息时，旧计时被新一轮从零开始的计时替换，且延迟 SSE 仍能正常接收和显示。

- **AC21（F13、N12）**  
  模拟服务将包含标题、粗体、斜体、行内代码、围栏代码块、列表、引用和链接的回答拆成多个 SSE 增量发送，其中 Markdown 标记跨增量拆分。结束事件到达前，终端按接收顺序显示未经解析的流式原文且不丢失内容；结束事件到达后，回答被一次性替换为整体 Markdown 渲染结果，各结构以对应的终端格式显示，Thinking 内容始终保持纯文本。

- **AC22（F2、F3）**  
  配置文件同时包含一个完整有效的活动配置和一个未激活配置，未激活配置可以缺少 `protocol`、`model`、`base_url`、`api_key` 等字段，也可以包含无效协议、缺失环境变量或不适用于其协议的 `thinking` 值；YCode 仍使用活动配置正常启动且不解析未激活配置的环境变量。将 `active` 切换到该未完成配置并重启后，YCode 才针对它显示具体校验错误并以非零状态退出。

- **AC23（F14、N13）**  
  在 Windows ConPTY 中启动 YCode 并停留在输入状态时，终端按顺序同时显示普通上横线、带蓝色 `❯` 和 `Send a message...` 的输入行、等宽普通下横线，以及下方独立的 `? for help`。横线没有反色背景、工具栏色块或左右竖边；输入提交或安全退出后不残留动态提示区域。本期输入 `?` 只作为普通消息提交，不触发帮助或 Skill 行为。测试可以通过内部样式入口替换横线颜色，并观察上下横线同时采用新颜色而提示文字样式不受影响。

- **AC24（F15）**  
  提交用户消息后，滚动区显示与输入区等宽的无边框背景板、蓝色 `❯` 和消息正文；多行正文保持在背景板内并对齐，不出现 `You` 标签。终端不支持 Unicode 时使用 `>`。
