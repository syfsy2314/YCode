# YCode MCP 客户端与延迟工具加载 Spec

## 背景

YCode 已具备统一的工具注册、参数校验、权限审批、并发调度和 Agent 工具调用循环，
但目前只能使用内建工具，无法连接外部 MCP Server。

用户需要通过项目配置声明多个 MCP Server，由 YCode 自动完成协议兼容、连接管理、
工具发现和适配，使 Agent 能以统一方式调用远端工具。外部工具必须继续经过现有权限
入口。

MCP Server 可能提供大量工具。如果把所有完整 Schema 提前发送给模型，会增加 Token
消耗、挤占上下文并降低工具选择准确性，因此需要客户端侧的按任务延迟加载机制。

## 目标

- 支持 stdio 和 Streamable HTTP 两种标准传输。
- 自动兼容 2026-07-28 与 2025-11-25 两代 MCP 协议。
- 发现多个已启用 Server 的工具，并以 `mcp_<server>_<tool>` 名称注册。
- Registry 保留完整工具目录，但完整 MCP Schema 默认不进入模型工具列表。
- 模型先看到 MCP 工具名称，通过 ToolSearch 发现需要的工具。
- 已发现工具从下一轮开始以完整 Schema 暴露，并仅在当前用户任务内保持可见。
- 单个 Server 故障不影响 YCode、内建工具和其他 Server。
- 缓存连接与工具目录，避免重复启动、连接和发现。
- 所有远端工具默认不可信，复用现有权限审批；项目可显式允许特定工具用于
  plan-only，但仍需审批并串行执行。
- 提供启动摘要和 `/mcp` 状态查询。
- 支持项目 `.env`，为大模型 API Key 和 MCP 配置提供敏感变量。

## 功能需求

### F1：项目配置与 `.env`

YCode 在现有 `.ycode/config.yaml` 顶层接受多个 MCP Server 配置。

- 每个 Server 使用唯一的项目内名称。
- 每个 Server 可以通过 `enabled` 布尔字段控制是否启用，默认值为 `true`。
- stdio 配置包括命令、参数、环境变量和超时。
- Streamable HTTP 配置包括 URL、自定义 Header 和超时。
- 启动时自动读取项目根目录 `.env`。
- `${VARIABLE}` 优先从系统环境变量取值，其次从 `.env` 取值。
- `.env` 可为 Anthropic API Key、stdio 环境变量和 HTTP Header 提供值。
- `enabled: false` 的 Server 不解析其敏感环境变量，不连接、不发现工具，也不向
  Registry 注册工具。
- 不得在终端、日志或错误中显示展开后的敏感值。
- 顶层 YAML 或 `.env` 格式错误阻止启动；单个 MCP Server 缺少引用变量时只停用
  该 Server。

### F2：标准传输

- stdio：启动本地子进程，通过标准输入输出通信，标准错误用于日志。
- Streamable HTTP：连接远端 MCP 端点，支持普通 JSON 响应和请求级 SSE 响应。
- HTTP 自定义 Header 支持 `${VARIABLE}` 插值，用于 Bearer Token 和 API Key 等认证
  方式。
- 首版不实现 OAuth 登录流程。

### F3：协议自动兼容

- 优先使用 MCP 2026-07-28。
- Server 不支持新版时，自动回退到 2025-11-25 初始化握手。
- 用户不需要配置协议版本。
- 首版只声明工具客户端所需能力。
- 不向 Server 提供 roots、sampling 或 elicitation。
- 能安全接收响应及协议允许的进度、日志和变更通知。

### F4：启动发现与固定目录

- 启动时只连接所有已配置且启用的 Server，并完整读取分页工具列表。
- 未启用 Server 保留为配置状态，不计为启动成功或失败；修改 `enabled` 后重启 YCode
  生效。
- 当前 YCode 进程内缓存工具目录。
- 运行期间收到工具列表变化通知时不动态更新。
- Server 工具变化在重启 YCode 后生效。
- 单个工具定义无效时排除该工具并报告原因，不影响同一 Server 的其他有效工具。

### F5：名称适配

远端工具以稳定名称暴露：

```text
mcp_<server_name>_<normalized_tool_name>
```

- Server 名称必须满足项目命名约束。
- 远端名称中的大小写、连字符和点转换为稳定的 snake_case 名称。
- 保留暴露名称到原始 Server、原始工具名的反向映射。
- 两个远端名称规范化后冲突时，两者均不注册，并报告具体冲突。
- 不允许覆盖内建工具或其他 Server 已注册的名称。

### F6：统一工具适配

每个有效 MCP 工具包装为 YCode 的统一工具：

- 保留远端名称、描述和输入 Schema。
- Agent 调用时先按 Schema 校验参数，再发送 `tools/call`。
- 文本结果正常返回给 Agent。
- 结构化 JSON 结果以可读 JSON 和结构化元信息返回。
- 图片、音频等首版不支持的内容只返回类型和 MIME 摘要，不传递 Base64 正文。
- MCP 工具错误、协议错误、连接错误和超时转换为稳定的 YCode 工具错误。

### F7：延迟 Schema 暴露

- 所有 MCP 工具注册时都标记为延迟工具。
- Registry 始终保存完整定义，但模型初始工具列表不包含其完整 Schema。
- 每轮 system reminder 按稳定顺序列出当前模式可以搜索的 MCP 工具名称。
- 内建 ToolSearch 始终直接可见，用于从本地 Registry 查找并激活延迟工具。
- ToolSearch 不重新连接 Server，也不重新调用 `tools/list`。
- ToolSearch 结果只返回名称、简短描述和加载状态，不把完整 Schema 写进对话历史。
- 被激活工具从下一模型轮次开始进入正常工具列表。
- 同一批次中绕过 ToolSearch 直接调用隐藏工具时，返回稳定的“工具尚未发现”错误。
- 首次加入新 Schema 时允许 Prompt Cache 失效一次；工具集合不变时保持稳定顺序以
  继续复用缓存。

### F8：任务级可见状态

- 每个用户任务开始时创建独立的空“已发现工具”集合。
- ToolSearch 只修改当前任务的可见集合，不修改工具对象或全局 Registry。
- 已激活工具在该任务的所有后续 Agent 轮次中保持可见。
- 任务正常完成、失败或取消后丢弃该集合。
- 下一个用户任务重新从延迟状态开始。
- 清空可见状态不删除工具、不关闭连接，也不清除启动时发现的工具目录。

### F9：权限与 plan-only

- MCP Server 提供的安全注解一律视为不可信。
- 所有 MCP 工具默认使用未知安全分类，在 Agent 模式下默认要求人工审批，并串行执行。
- 现有项目安全规则可以按 `mcp_*` 名称显式允许或拒绝。
- plan-only 默认不能搜索或调用 MCP 工具。
- 项目安全配置可以把特定 `mcp_*` 工具声明为“允许在 plan-only 使用”。
- 该声明只解除 plan-only 可见限制，不把工具变成普通只读工具；调用时仍必须人工审批
  并串行执行。
- 安全配置引用暂时不可用的 `mcp_*` 工具时显示警告但继续启动。
- 内建工具名称或参数配置错误仍按现有规则阻止启动。
- ToolSearch 只读取本地目录，不调用远端服务，不需要 MCP 工具审批。

### F10：超时与取消

每个 Server 分别支持：

- 启动和工具发现超时，默认 10 秒。
- 单次工具调用超时，默认 60 秒。
- 两类超时都可按 Server 覆盖。
- 用户取消 Agent 任务时，取消正在等待的 MCP 请求。
- 已取消或超时的工具调用不得在客户端自动重试。

### F11：连接复用与恢复

- 每个 stdio Server 在 YCode 进程内复用同一个子进程和客户端连接。
- Streamable HTTP 复用 HTTP 客户端连接池，但新版协议不虚构 MCP session。
- 旧版 HTTP Server 按协议保存和复用其 session。
- 连接中断时，当前工具调用返回连接错误，不自动重试。
- 后续调用前允许重新建立连接并重新完成必要的协议协商。
- 重连不改变当前进程缓存的工具目录。

### F12：降级启动

- 每个已启用 MCP Server 独立连接和发现。
- 单个 Server 配置、连接、协商或发现失败时，将其标记为不可用并显示原因。
- 其他 MCP Server、内建工具和 YCode 主流程继续可用。
- 所有 MCP Server 均失败时，YCode 仍可只使用内建工具启动。

### F13：状态查询与关闭

- 启动时显示 MCP Server 成功数、失败数和简要原因。
- `/mcp` 不调用模型、不进入对话历史。
- `/mcp` 显示每个 Server 的名称、传输方式、当前状态、发现的有效工具数量和最近错误；
  未启用 Server 显示为“未启用”。
- 状态输出不得包含环境变量值、认证 Header 或其他凭据。
- YCode 退出时关闭 HTTP 客户端，并关闭 stdio 输入、等待子进程退出；必要时终止未
  退出的子进程。
- 关闭操作应可重复执行且不会重复释放资源。

## 非功能需求

### N1：协议正确性

- 两种传输都必须遵循对应 MCP 版本的消息格式、生命周期和取消规则。
- 并发请求的响应必须按 JSON-RPC ID 正确关联，不得串包或误交付。
- 迟到响应、未知 ID、重复响应和非法消息不得导致 YCode 崩溃。
- 协议版本不兼容时必须产生明确错误或按规则回退，不能静默使用错误语义。

### N2：异步与取消安全

- 工具调用、连接读取和关闭不得阻塞 Agent 事件循环。
- 用户取消后，不得继续启动尚未执行的远端调用。
- 已取消请求的迟到结果不得进入 Agent 历史。
- 取消、超时和正常响应竞争时，只允许一个终态生效。

### N3：副作用安全

- 不得自动重试结果不确定的 MCP 工具调用。
- 连接断开不能被解释为工具未执行。
- 延迟工具未在当前任务激活时，即使模型构造出正确名称和参数也不得执行。
- 权限审批必须发生在发送远端 `tools/call` 之前。

### N4：故障隔离

- 一个 Server 的配置、协议、Schema、连接或运行错误不得污染其他 Server。
- stdio 子进程输出非法内容时，只影响对应 Server。
- HTTP 返回异常状态、非法 Content-Type 或损坏的 SSE 时，只终止对应请求或连接。
- 降级启动后，内建工具行为必须与未配置 MCP 时一致。

### N5：资源与性能

- 多个 Server 的启动和发现应并发进行，启动耗时不应简单累加所有 Server 的超时。
- 同一 stdio Server 不得为每次调用重复创建子进程。
- HTTP 应复用底层连接。
- ToolSearch 只查询本地缓存目录，不产生网络请求。
- 退出、异常和取消后不得遗留子进程、读取任务或 HTTP 连接。

### N6：上下文与缓存效率

- 未发现 MCP 工具不得把完整描述和 Schema 放入模型工具列表或对话历史。
- system reminder 只包含稳定排序的工具名称和必要说明。
- ToolSearch 结果保持简短，不重复输出完整 Schema。
- 工具列表只有在当前任务首次激活新工具时变化。
- 相同可见工具集合必须产生内容与顺序一致的模型工具列表，以利于 Prompt Cache。

### N7：确定性

- 相同配置和工具目录必须产生相同的公开工具名。
- 名称规范化、冲突处理、搜索结果排序和 Schema 暴露顺序必须可重复测试。
- ToolSearch 不得因字典遍历顺序或异步发现完成顺序产生随机结果。
- 当前任务的可见状态不得泄漏到下一任务或其他会话。

### N8：敏感信息保护

- `.env`、stdio 环境变量和 HTTP Header 的展开值不得出现在日志、状态页面或 Agent
  工具结果中。
- stdio 的 `stderr` 和远端错误内容按不可信输入处理。
- 远端工具名称、描述、Schema 和返回结果不得改变本地权限分类。
- MCP Server 不得通过工具注解自行获得 plan-only 或免审批权限。

### N9：兼容性与回归

- 当前阶段只在 Anthropic Agent 路径接入和验证 MCP。
- 供应商无关的工具、Registry 和延迟暴露状态不得依赖 Anthropic 专用类型。
- 不新增 OpenAI 专用配置、协议转换或验收场景。
- 现有六个内建工具、权限系统、plan-only、工具调度和对话流程不得回归。
- 未配置 `mcp_servers` 时，启动与运行行为应保持不变。

### N10：可诊断性

- 用户可区分配置错误、环境变量缺失、协议不兼容、发现失败、连接中断、调用超时和
  远端工具错误。
- 错误信息包含 Server 名称和稳定错误类别，但不泄露内部异常或凭据。
- `/mcp` 状态必须与当前真实连接状态一致。
- Server 恢复或再次断开后，状态能够及时更新。

### N11：可验证性

- stdio、Streamable HTTP、新旧协议和自动回退均需自动化验证。
- 延迟暴露、ToolSearch 激活、跨任务清空和隐藏工具执行拒绝需有单元及集成测试。
- 必须验证请求 ID 异步匹配、超时、取消、断线和迟到响应。
- 必须验证 `.env` 优先级、敏感值脱敏、名称冲突和 Server 故障隔离。
- 至少包含一个真实 Windows 交互式端到端场景，覆盖 MCP 工具搜索、审批和调用。

## 不做的事

- 不支持 MCP Resources、Prompts、Completions 等非工具能力。
- 不向 MCP Server 提供 roots、sampling、elicitation 或模型代理调用。
- 不实现 MCP OAuth、浏览器登录、授权回调或 Token 自动刷新；首版只支持配置 HTTP
  Header。
- 不支持已废弃的 HTTP+SSE 传输，也不保证兼容 2025-11-25 与 2026-07-28 之外的协议
  版本。
- 不监听并动态应用运行期工具列表变化；工具目录只在 YCode 启动时发现。
- 不使用 Anthropic 原生 Tool Search 或 `defer_loading`；延迟加载由 YCode 客户端实现。
- 不把图片、音频或其他二进制 MCP 结果直接传给模型。
- 不根据远端工具注解自动判定只读、写入或危险等级。
- 不自动重试超时、断线或结果未知的工具调用。
- 不在多个用户任务间保留已发现工具状态。
- 不实现已发现工具的数量上限、LRU 淘汰或手动清理。
- 不把 MCP 工具目录或连接状态持久化到磁盘。
- 不支持用户级全局 MCP 配置、项目与全局配置合并或配置继承。
- 不支持运行期间切换 Server 的 `enabled` 状态或热重载 MCP 配置。
- 不提供 MCP Server 安装、下载、市场、自动升级或配置编辑界面。
- 不新增 OpenAI 工具调用、MCP 适配、专用配置或验收场景。
- 不改变现有内建工具的名称、Schema、权限分类或执行行为。

## 验收标准

### AC1：配置与 `.env`

- 项目根目录 `.env` 中的变量可用于活动 Anthropic API Key、stdio 环境变量和 HTTP
  Header。
- 系统环境变量与 `.env` 重名时使用系统环境变量。
- `enabled` 缺省时 Server 正常启用；显式设为 `false` 时，即使其敏感变量缺失，也不
  解析、不连接、不发现或注册工具。
- 未配置 MCP 时，现有配置和启动行为保持不变。
- 状态、错误和日志中找不到任何展开后的敏感值。

### AC2：两种传输

- 配置 stdio Server 后，YCode 能启动子进程、发现工具并完成调用。
- 配置 Streamable HTTP Server 后，YCode 能处理 JSON 和请求级 SSE 响应。
- HTTP 自定义 Header 能正确发送，但不会显示在 `/mcp` 状态中。

### AC3：协议自动兼容

- 面对 2026-07-28 Server 时使用新版无状态流程。
- 面对 2025-11-25 Server 时自动回退并完成初始化握手。
- 两种 Server 使用相同项目配置，不需要用户指定版本。
- Server 请求未声明的客户端能力时被安全拒绝。

### AC4：多 Server 与降级启动

- 多个 Server 可同时连接、发现和调用。
- 未启用 Server 不参与连接和启动成功/失败计数，并可在 `/mcp` 中识别为“未启用”。
- 一个 Server 超时、退出或返回非法协议消息时，其他 Server 与内建工具继续可用。
- 所有 MCP Server 均失败时，YCode 仍能启动并使用内建工具。
- 启动摘要准确显示成功数、失败数和脱敏原因。

### AC5：工具目录与名称

- 分页工具列表被完整读取。
- 远端工具稳定映射为 `mcp_<server>_<tool>`。
- 大小写、连字符和点按统一规则规范化。
- 规范化冲突、非法 Schema 和重复名称被排除并显示明确原因。
- 运行期工具列表变化在重启前不改变当前 Registry。

### AC6：初始延迟暴露

- MCP 工具已存在于 Registry，但第一次模型请求不包含其完整 Schema。
- system reminder 只按稳定顺序列出允许搜索的 MCP 工具名称。
- 内建工具和 ToolSearch 正常出现在初始工具列表。
- 初始请求的工具 Schema 大小不随 MCP 工具完整 Schema 总量线性增长。

### AC7：ToolSearch 激活

- 模型调用 ToolSearch 后，结果只包含匹配名称、简短描述和加载状态。
- ToolSearch 结果不包含完整 Schema，也不产生 MCP 网络请求。
- 被发现工具的完整 Schema 出现在同一用户任务的下一次模型请求中。
- 模型随后能以普通 `mcp_*` 工具调用方式执行该工具。
- 同一批次绕过搜索直接调用隐藏工具时，得到稳定的“尚未发现”错误且远端没有副作用。

### AC8：任务级状态

- 同一用户任务的后续 Agent 轮次持续包含已发现工具。
- 任务完成、失败或取消后，可见集合被丢弃。
- 下一条用户消息的第一次模型请求不包含上一任务发现的完整 MCP Schema。
- Registry、工具目录和 MCP 连接没有因可见集合清空而被删除或重建。

### AC9：工具参数与结果

- 调用参数不符合远端 Schema 时，在发送 `tools/call` 前返回校验错误。
- 文本和结构化 JSON 结果能被 Agent 正确理解。
- 图片和音频结果只产生类型及 MIME 摘要，不包含 Base64 正文。
- MCP 工具错误、协议错误和 YCode 连接错误能被明确区分。

### AC10：权限与 plan-only

- 未配置安全规则的 MCP 工具在 Agent 模式下触发人工审批并串行执行。
- 拒绝审批时不发送远端 `tools/call`。
- MCP Server 的只读注解不会自动改变本地权限。
- plan-only 默认无法搜索或调用 MCP 工具。
- 本地显式允许后，指定工具可以在 plan-only 中被搜索，但实际调用仍需审批并串行执行。
- 安全配置引用暂时不可用的 `mcp_*` 工具时只产生警告。

### AC11：超时、取消与异步匹配

- 启动发现和工具调用分别使用对应超时。
- 多个并发 JSON-RPC 请求的响应按 ID 返回给正确等待者。
- 超时、取消、迟到响应和连接关闭竞争时，每个调用只产生一个终态。
- 用户取消后，迟到结果不会写入 Agent 历史。
- 超时或连接错误不会自动重试工具调用。

### AC12：断线恢复

- stdio 子进程或 HTTP 连接中断时，当前调用返回连接错误。
- 当前调用不会因重连而重复执行。
- 后续调用可以重新连接并成功执行。
- 重连不重新暴露全部 MCP Schema，也不改变启动时缓存的工具目录。

### AC13：缓存稳定性

- 当前任务没有发现新工具时，连续模型请求的工具列表内容与顺序一致。
- 首次发现新工具后，下一轮工具列表只增加对应工具。
- 新集合保持不变后，后续请求继续使用相同工具列表。
- ToolSearch 不会重复激活已经发现的工具。

### AC14：状态与资源关闭

- `/mcp` 不调用模型、不进入历史，并显示每个 Server 的传输、状态、工具数量和最近
  错误。
- Server 断开与恢复后，`/mcp` 显示最新状态。
- 正常退出和异常退出均关闭 HTTP 连接与 stdio 子进程。
- 重复关闭不会报错，也不会遗留后台读取任务。

### AC15：端到端与回归

- 真实 Windows 终端中可完成：启动 → 查看 MCP 状态 → 发送任务 → ToolSearch → 审批
  → 调用远端工具 → 获得最终回答。
- 2026-07-28 与 2025-11-25 至少各有一个完整自动化端到端场景。
- 现有格式检查、静态检查、编译检查和完整测试全部通过。
- 未配置 MCP 时，现有 Anthropic 工具循环、权限审批、plan-only 和六个内建工具行为
  不变。
